# Mac App Store privacy assessment (candidate)

Prepared 2026-10-02 against the first `mac-app-store` build. This is source-code evidence and a proposed App Store Connect response, not a published privacy label or legal export classification. The subsequent public policy and signed-package checks are recorded in [validation](../VALIDATION.md). Recheck the archive and any added SDKs before publication.

## Data flow and candidate label

The app reads user-authorized local agent files, creates local snapshots and sends XChaCha20-Poly1305-encrypted snapshot and device-report bodies to a Google Drive folder chosen or created by the user. The Drive API request still exposes account-linked file/folder IDs, plaintext folder names when the app creates a folder, generated object names, MIME types, sizes and request metadata to Google. The developer does not run a content or telemetry backend in this code. The Google `about` response returns the account permission ID, display name and email to the app for local identification; this code does not send those fields to Bastet. OAuth credentials and the space key use the local credential store. Store builds exclude Agent Memory OS sync and the direct updater.

The conservative candidate for App Store Connect is **Yes, data collected**, with **Other User Content** (a user-supplied Drive folder name can remain readable at Google) and **Other Data Types** (Drive object/service metadata, including names, IDs and sizes), both **linked to the user**, **App Functionality** only, **not used to track**. This treats Google as the relevant external service partner for the app's cloud feature. The app's manifest records these categories. The encrypted snapshot body is not itself the reason for claiming readable content collection: the developer and Google lack the space key in this design, but other people whom the user gives both Drive and key access can read it. The label describes the broad data categories and does not communicate the encryption details; the policy draft does.

Do **not** add Name, Email Address or User ID solely because the app reads them from Google's `about` endpoint for local display and account checks; this code does not transmit those returned values to Bastet or to a new destination. Do **not** add Device ID solely for the app-generated ID inside the encrypted report, or analytics/diagnostics for local journals. The account used to authorize Drive is inherently known to Google; the owner should verify Google's data role and exact final request behavior before publishing the candidate response. If the final binary or support process sends any readable contact information, diagnostics, local filenames or selected content to the developer or another service, revise the manifest and label.

Apple defines collection as off-device transmission that allows the developer or a third-party partner to access data beyond servicing the request in real time, and requires data collected for app functionality to be disclosed. Apple also says data processed solely on the device is not collected. This candidate treats the readable, retained Drive metadata as collected even though no Bastet server receives it. [Apple's privacy definitions](https://developer.apple.com/app-store/app-privacy-details/) and [App Store Connect privacy workflow](https://developer.apple.com/help/app-store-connect/manage-app-information/manage-app-privacy/) govern the final questionnaire. The latter requires a publicly accessible privacy-policy URL for macOS; the published policy is now available at [the product website](https://bastet.tw/agent-sync/privacy/), and the repository assessment remains supporting evidence.

## Privacy manifest and required-reason APIs

`src-tauri/PrivacyInfo.xcprivacy` records no tracking and the two conservative collection categories above. It must be copied to the final macOS app's `Contents/Resources/PrivacyInfo.xcprivacy`. A source file alone is not an embedded manifest; inspect the signed archive. Apple says macOS apps put the file in `Contents/Resources`, and Tauri's resource map can place a file at that path. [Apple bundle placement](https://developer.apple.com/documentation/bundleresources/adding-a-privacy-manifest-to-your-app-or-third-party-sdk); [Tauri resources](https://v2.tauri.app/develop/resources/).

No `NSPrivacyAccessedAPITypes` are asserted for this macOS-only build. Apple's current required-reason API documentation applies those declarations to iOS, iPadOS, tvOS, visionOS and watchOS; its collected-data manifest categories apply on all platforms. The Rust code does read file metadata/timestamps, often for picker-granted files, but that does not make a macOS required-reason declaration mandatory. If an iOS-family target is later added, audit the complete linked binary and SDK manifests against Apple's then-current categories and approved reasons. For example, `3B52.1` covers timestamps of files the user specifically granted access to, and `C617.1` covers app-container files; declaring either without confirming every use would be inaccurate. [Apple privacy manifest scope](https://developer.apple.com/documentation/bundleresources/privacy-manifest-files); [required-reason API policy](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api); [API categories and reasons](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype).

## Export and other submission questions

The app implements XChaCha20-Poly1305 with a Rust crate as well as HTTPS transport; it is more than Apple's built-in operating-system crypto alone. Do not set `ITSAppUsesNonExemptEncryption` to `false` simply to bypass the export questions. Answer App Store Connect's actual encryption questionnaire for the final build and territories, provide any documentation it requires, and only then set the appropriate Info.plist value or approved documentation key. Apple's review is case by case, and the developer bears responsibility for the classification. [Apple export overview](https://developer.apple.com/help/app-store-connect/manage-app-information/overview-of-export-compliance/); [documentation workflow](https://developer.apple.com/help/app-store-connect/manage-app-information/determine-and-upload-app-encryption-documentation/).

Apple's Content Rights field covers apps that contain, show or access third-party content. The app accesses files generated by third-party agent products on the user's authorization. The literal field therefore needs an owner determination of the right to access and distribute that content in the offered territories; code review cannot certify those rights. Private, user-selected Drive sync does not appear to be Apple's age-rating **User-Generated Content** capability, which Apple defines as broad distribution of content created by users as part of the intended experience. Confirm the final UI does not add public discovery or redistribution before answering. [Apple Content Rights](https://developer.apple.com/help/app-store-connect/reference/app-information/app-information); [age-rating capability definition](https://developer.apple.com/help/app-store-connect/reference/app-information/age-ratings-values-and-definitions).

Before the final responses: confirm Google/other vendor data practices for this integration, inventory final bundled frameworks and SDK manifests, verify the signed app contains this file at Apple's required path, and publish a policy URL matching the final build. These checks can change the label; a saved draft is not evidence of App Review approval.

## Observed submission draft

On 2026-10-02, App Store Connect saved the two proposed collection categories as an unpublished draft; no privacy policy URL or published label was asserted. The age questionnaire calculated a global 4+ rating, with regional variations. Content-rights owner confirmation remains pending.

In an unsaved encryption-documentation walkthrough, selecting non-standard and non-OS standard encryption plus France distribution made Apple request both BIS CCATS approval and a French encryption declaration in one ZIP or PDF. The form was cancelled without submitting a classification or document. The [XChaCha IETF document](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-xchacha-03) is an expired draft; the standard ChaCha20-Poly1305 RFC does not establish identical status for XChaCha20. This evidence requires an applicable export-classification determination rather than an automatic exemption flag.

On the same date, the public product/privacy pages were deployed and policy/control URLs were saved in all five Store locales. This supersedes the earlier missing-URL status; the privacy label itself remains unpublished.
